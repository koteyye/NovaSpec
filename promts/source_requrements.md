# Первичный требования для NovaSpec
В папке nova-spec-ide-studio лежит проект UI написанный на Type Script - это полностью готовый UI для разрабатываемого приложения но без бизнес-логики, его необходимо в точности как оно есть переписать на Flutter (но при этом не забывать соблюдатель паттерны Flutter).

Полностью, без каких либо предположений изучи весь проект Type Scrypt

Далее описаны каждые элементы приложения на UI с его бизнес логикой:
# Онбординг
Появляется, когда пользователь впервые открывает приложение (в hive хранилище нет никакого конфига).

Онбординг состоит шагов:
## Проект
Пользователю предлагается создать проект или открыть существующий (проектом является папка на его диске, он может либо создать новую папку если нажмет новый проект или открыть существующую папку).
### Создать новый проект
Пользователь указывает имя проекта
Путь к папке: указывает путь к папке где будет сохранен проект или нажимает кнопку Обзор после чего откроется проводник операционной системы, пользователь выбирает папку и путь к этой папке записывается в поле.
В выбранной папке создается папка проект (с названием, которое указано в имени проекта)

### Открыть существующий проект
Сразу открывается проводник операционной системы, где пользователь выбирает папку, которую откроет в приложении

### Итог
Когда пользователь создал проект или открыл папку, это сразу же должно записаться в Hive конфиг пользователя. Если он откроет приложение повторно, то ему этот же проект должен открыться

## Настройка ИИ и интеграции
На данном шаге пользователю предлагается перейти к настройкам ИИ или пропустить данный шаг.
### Пропустить
Онбординг закрывается
### Настроить
Открывается окно настроек (тоже самое, которое находится по пути Настройки -> Параметры)

#### Базовый URL
Пользователь указывает URL на Confluence, к которому хочет подключиться
Необходимо учесть определение типа инстанса по URL который указал пользователь:
```
Как определить тип инстанса
Если домен вида <org>.atlassian.net и URL страниц содержит /wiki, это Confluence Cloud; базовый путь для API всегда включает /wiki для облака.

Если домен кастомный (например, confluence.company.com) и/или есть контекстный путь /confluence или /wiki на собственном домене, это Data Center/Server.

Формирование базового URL
Cloud: https://<site>.atlassian.net/wiki/api/v2 для v2 и https://<site>.atlassian.net/wiki/rest/api для v1; менять нужно только <site>.

Data Center/Server: {baseUrl}/rest/api, где {baseUrl} — адрес инстанса с портом и контекстом, например https://confluence.company.com или http://confluence.company.com:8090/confluence.

Автоопределение в коде
Правило: если host оканчивается на atlassian.net — использовать Cloud шаблон с префиксом /wiki/...; иначе брать «siteUrl» целиком как baseUrl и добавлять /rest/api для DC/Server.

Для DC/Server безопасно верифицировать baseUrl запросом GET {baseUrl}/admin/viewgeneralconfig.action в интерактивном сценарии или через конфиг админа; этот URL помогает убедиться в корректности контекстного пути.
```

## Кнопка "Проверить"
По данной кнопке выполняется вызов кадого сервиса, по которым пользователь задал настройки.
Например по провайдера - вызывается API выбранного провайдера на запрос моделей
По  Интеграции с Confluence вызывается API для полученич списка пространств
По Музикации вызывается gen-api.ru по следующему примеру:
```curl
curl --request GET \
  --url https://api.gen-api.ru/api/v1/user \
  --header 'Authorization: Bearer <token>' \
  --header 'User-Agent: insomnia/11.6.1'
```
Пример ответа:
```json
{
	"name": "Kotey Ye",
	"email": "koteyye@gmail.com",
	"phone_number": null,
	"balance": 33,
	"email_verified_at": "2025-09-21T12:19:51.000000Z",
	"created_at": "2025-09-21T12:19:51.000000Z"
}
```
Кстати, этот же метод возвращает текущийм баланс (поле balance в ответе), которые дальше понадобится для индикатора

### По всем вызовам вернуля 200 (успешно)
Показывается уведомление, что все интеграции успешно прошли проверку

### Хотя по одному из вызовов вернулось не 200 (не успешно)
Позазываем уведомление, что <название интеграци - провайдер, confluence или музикация> не прошел проверку: <подробная ошибка от сервиса, почему не прошла ошибка>

## Кнопка "Сохранить"
Сохраняет все настройки в конфигурацию Hive
По умолчанию недоступна, сохранить можно только после выполнения проверки интеграции (кнопка "Проверить").
Если проверка пройдена успешно, то кнопка "Сохранить" доступна
Если проверка не пройдена, то кнопка "Сохранить" задизейблена
Если пользователь вышел из окна паретров не сохранив, то изменения не сохраняются в Hive

# Проводник
Статично указан логотип и название приложения NovaSpec
Далее идет открытая папка проекта
В папке представлены файлы для отображения
Для поддерживаемых файлов есть свои иконки (есть в ts проекте, их надо переиспользовать в flutter)
Поддержваемые форматы:
.md .html .json .mp3 .xml .txt
Все остальные форматы отображаются в виде дефолтной иконки

Кликнув по файлу в проводнике он откроется в рабочей зоне на отдельной вкладке

# Рабочая зона
В зависимости от открываемого формата файла, он по разному открывается в рабочей зоне:
## .md и .html
Открывается в режиме рендера
При необходимости можно переключить в режим редактирования, тогда файл открывается в режиме редактирования кода используя библиотеку flutter_code_editor
Еще у открытого .md и .html, если включена "Музикация", то должна быть доступна кнопка-иконка музицировать.
### Музицировать
При нажатии на кнопку открывается окно "Музицировать документ" (реализован в ts)
Если нажать нет, то окно закрывается и ничего не происходит
Если нажать Да, то выполняется ряд действий, на каждое выполняемое действия снизу подсвечивается состояние:
#### Генерирую Lyrics
Выполняется запрос в текущую модель (та же модель, что выбрана для AI-ассистент) из конфига.
Промт для модели:
```promt
Составь текст песни, чтобы зачитать данные требования в жанре {текущий жанр в конфиге}.
Текст должен быть сделан в виде Lyrics пригодным для Suno
В ответе не указывай ничего лишнего, исключительно Lyrics
Требования: {требования из открытого файла, который пользователь хочет музицировать}
```
#### Гененрирую музыку в Suno
Выполняется запрос на генерацию песни в Suno через gen-api.ru
```
curl --request POST \
  --url https://api.gen-api.ru/api/v1/networks/suno \
  --header 'Authorization: Bearer {token из конфига}' \
  --header 'Content-Type: application/json' \
  --data '{
    "title": "Свобода",
    "tags": "${жанр из конфига}",
    "prompt": "${Lyrics которую ранее сгенерировали}",
    "translate_input": false,
    "model": "v5"
}'
```
Далее анализируем коды ответа:
##### 200 или 201
Запрос принят, получаем такое тело ответа:
```
{
	"request_id": 28104643,
	"model": "suno",
	"status": "processing"
}
```
По данному телу ответу сохраняем временно request_id, он потребуется для отслеживания результата генерации
##### 402
Недостаточно средств на балансе gen-api
##### Остальные коды ошибок:
400	Запрос с таким request_id не найден
401	В запросе нет токена авторизации (Не указан Authorization: <Bearer token>) или токен неверный или тех. работы. Конкретная причина будет указана в теле ответа.
404	Указана несуществующая нейросеть
503	Непредвиденная ошибка, обратитесь в службу поддержки
419	Непредвиденная ошибка, обратитесь в службу поддержки
419	Слишком много запросов

### shelf_swagger_ui
Ниже — практичная инструкция, как встроить локальный Swagger UI на базе shelf_swagger_ui, запускать его фоном в приложении и автоматически открывать его в WebView при выборе OpenAPI YAML/JSON файла.​

Архитектура
В приложении запускается фоновый shelf‑сервер с хендлером SwaggerUI, который рендерит выбранную OpenAPI спецификацию из файла.​

Экран с WebView открывает локальный URL (например, http://127.0.0.1:4001), показывая интерактивную документацию Swagger UI.​

Зависимости
Добавить в pubspec.yaml: shelf, shelf_swagger_ui, webview_flutter и разрешения для Интернета на Android/iOS, чтобы WebView грузил локальный эндпоинт.​

Убедиться, что включена поддержка JavaScript в WebView, иначе Swagger UI не будет работать корректно.​

Сервис фона (shelf)
Создать сервис Dart, который: принимает путь к YAML/JSON, создает SwaggerUI.fromFile(File(path), title: ...), поднимает io.serve(handler, host, port), хранит ссылку на HttpServer.​

Реализовать методы start(path), restart(newPath), stop(), чтобы при выборе другого файла спецификации просто перезапускать хендлер.​

Инициализация при старте
На старте приложения запустить сервис с дефолтной спецификацией (или без запуска до первого выбора файла), обработать ошибки порта/файла, логировать адрес сервера.​

Хост: 127.0.0.1; Порт: 4001 (или динамический с поиском свободного порта), чтобы WebView стабильно открывал локальный URL.​

Обработчик выбора файла
При выборе файла .yaml/.yml/*.json валидировать, что это OpenAPI 3.x (минимально — наличие ключей openapi/info/paths) и передать путь в сервис.restart(path).​

После перезапуска сервиса открыть экран с WebView, указывая URL локального сервера, и обновить страницу при завершении загрузки (onPageFinished) при повторных открытиях.​

Экран WebView
Использовать WebView(initialUrl: 'http://127.0.0.1:4001', javascriptMode: JavascriptMode.unrestricted, navigationDelegate: ...).​

При необходимости настроить JavaScriptChannel для двусторонней связи (например, логирование событий UI, авторизация токеном), вызовы evaluateJavascript для вставки токенов.​

Авторизация и CORS
Если Try it out обращается к внешним сервисам, убедиться, что CORS разрешён на целевом API или проксировать запросы через сервер, который выставляет корректные заголовки.​

Для OAuth/Authorize убедиться, что редиректы и куки работают в WebView; возможно, понадобится отдельный экран авторизации и последующая передача токена в UI.​

Ошибки и перезапуск
Если файл недоступен/битый — показывать страницу с ошибкой и лог, не падать приложением; дать возможность выбрать другой файл и выполнить restart.​

При конфликте порта — выбрать другой порт и обновить URL в WebView; хранить текущий адрес в состоянии.​

Офлайн и ассеты
При желании упаковать swagger‑ui dist в ассеты и раздавать через shelf (статические файлы), чтобы UI работал офлайн; спецификацию читать из локального пути.​

WebView будет открывать тот же локальный URL, без зависимости от внешнего интернета, что ускоряет рендеринг и упрощает брендирование.​

Мини‑чеклист
Сервис shelf: start/restart/stop, хранение HttpServer, лог порта и пути к spec.​

Обработчик выбора файла: фильтр расширений, проверка ключей OpenAPI, вызов restart и открытие WebView.​

WebView: включён JS, обработка навигации, при необходимости JS‑каналы и evaluateJavascript для токенов.​

Этот подход даёт быстрый интерактивный Swagger UI внутри приложения без нативного рендера схемы, используя стабильный стек shelf + WebView и простое переключение между спецификациями.​

## SSE-интерфейс для взаимодействия с ИИ-агентом

### 1. Описание задачи

Реализовать канал односторонней потоковой передачи событий от ИИ-бэкенда к клиентскому приложению на основе Server-Sent Events (SSE) для отображения текстовых ответов, предложений по редактированию файлов, статусов генерации и ошибок.

### 2. Протокол обмена

#### 2.1. Транспорт

- Использовать HTTP/1.1 или HTTP/2 (желательно) с заголовком  
  `Content-Type: text/event-stream`.
- Ответ сервера должен быть «долгоиграющим» (keep-alive), без закрытия соединения после первого ответа.
- Запретить кэширование: `Cache-Control: no-cache, no-transform`.
- Для кросс-доменных сценариев корректно настроить CORS и, если нужно, поддерживать withCredentials.

#### 2.2. Формат событий

- Каждое событие состоит из:
  - Необязательного `event:` (тип события).
  - Необязательного `id:` (уникальный идентификатор).
  - Необязательного `retry:` (задержка для реконнекта).
  - Одной или нескольких строк `data:` — полезная нагрузка.
  - Двойной перевод строки завершает событие.

- В поле `data:` передавать **однострочный JSON-объект** следующей структуры:
  ```json
  {
    "type": "message|file_edit|status|error",
    "id": "string",
    "conversation_id": "string",
    "timestamp": 1712345678,
    "data": {
      "text": "string",
      "file_path": "string",
      "diff": "string",
      "status": "thinking|generating|done|failed",
      "error_message": "string"
    }
  }
  ```

- Для событий разных типов в поле data должны быть только соответствующие ключи:
  - `type: message` — `text` (обязательно)
  - `type: file_edit` — `file_path`, `diff`
  - `type: status` — `status`
  - `type: error` — `error_message`

- Все временные метки — в Unix-времени (секунды или миллисекунды UTC).

#### 2.3. Назначение event

- Поле `event:` выставляется согласно `type`, например:  
  `event: message`, `event: file_edit`, `event: status`, `event: error`.
- Клиентская логика должна слушать нужные типы через  
  `eventSource.addEventListener('message', ...)` и т.п.

#### 2.4. Взаимодействие

- Клиент инициирует поток через GET-запрос к `/api/stream/:conversation_id` или аналогичному endpoint.
- SSE соединение должно поддерживать авто‑реконнект: сервер выставляет `id` в каждом сообщении, чтобы клиент мог продолжить c нужной точки при потере соединения.
- При необходимости сервер периодически посылает heartbeats: пустые data-события или комментарии.

#### 2.5. Безопасность

- Авторизация производится перед/при открытии соединения (токен в header/cookie).
- Принять меры против CSRF (см. ограничения ввода).

#### 2.6. Примеры событий

```json
// Сообщение
data: {"type":"message","id":"msg-1","conversation_id":"abc","timestamp":1712345678,"data":{"text":"Текст ответа"}}

// Предложение изменить файл
data: {"type":"file_edit","id":"edit-1","conversation_id":"abc","timestamp":1712345680,"data":{"file_path":"src/App.js","diff":"@@"}}

// Статус
data: {"type":"status","id":"stat-1","conversation_id":"abc","timestamp":1712345679,"data":{"status":"generating"}}

// Ошибка
data: {"type":"error","id":"err-1","conversation_id":"abc","timestamp":1712345681,"data":{"error_message":"Ошибка"}}
```
— Каждое сообщение на отдельной строке data, события разделены двойным переводом строки согласно спецификации SSE.

#### 2.7. Клиентская обработка

- Создавать SSE-подключение через `EventSource`.
- Обрабатывать события по типу (через addEventListener по event или парс по `type`).
- Парсить каждое событие как валидный JSON, выводить, предлагать патчи, отображать статусы и ошибки.

### 3. Специфические требования

- Все изменения файлов предоставлять в формате unified diff (совместим с git, patch).
- Тестировать работоспособность потока в браузерах, через прокси/CDN, проводить нагрузочные тесты.

**Определение формата истории**
User Story используется, когда задача связана с конкретным пользователем или группой пользователей, которые взаимодействуют с системой. Формат: Я, как [роль пользователя], хочу [действие], чтобы [ценность].

Пример: Я, как администратор, хочу удалять обучения из специализации, чтобы студенты изучали только актуальные для них обучения.
Job Story используется, когда задача не связана с конкретным пользователем, а описывает системное поведение или интеграцию. Формат: Когда [событие], хочу [действие], чтобы [результат].

Пример: Когда внешняя система интегрируется с Docs, она должна иметь возможность получать информацию о подписанных документах, чтобы использовать эту информацию для валидации в бизнес-процессах.
Рекомендации по выбору формата
Если в задаче фигурирует конкретный пользователь или роль, используйте User Story.
Если задача описывает системное поведение без конкретного пользователя, используйте Job Story.
В случае сомнений, оцените, что является ключевым элементом задачи: пользователь или системное событие.

### 4. Критерии приемки

**Обязательный раздел.**

Критерии приемки — это ключевые условия, которые должны быть выполнены, чтобы считать User Story реализованной. Они служат основой для создания тест-кейсов и определяют, когда работа считается завершенной.

**Основные принципы формулирования критериев приемки:**

1. **Фокус на бизнес-ценности:**
   - Описывайте, какую пользу получит бизнес или пользователь
   - Формулируйте с точки зрения результата для пользователя, а не технической реализации
   - Пример: ✅ "Пользователь может найти нужный документ по его названию или дате создания"

2. **Ориентация на конечный результат:**
   - Избегайте технических деталей реализации
   - Описывайте, что должно быть достигнуто, а не как это должно быть сделано
   - Пример: ✅ "Система уведомляет пользователя о необходимости подписать документ"
   - Пример: ❌ "Система отправляет push-уведомление через Firebase Cloud Messaging"

3. **Измеримость:**
   - Критерии должны быть конкретными и проверяемыми
   - Должна быть возможность однозначно определить, выполнен критерий или нет
   - Пример: ✅ "Пользователь может отфильтровать документы по статусу подписания"

**Что НЕ должно быть в критериях приемки:**
- Технические детали реализации (они относятся к функциональным требованиям)
- Нефункциональные требования, такие как время отклика или производительность (для них есть отдельный раздел)
- Подробные описания UI/UX (они относятся к функциональным требованиям)

**Примеры хороших критериев приемки:**
- "Пользователь может видеть список всех своих документов, ожидающих подписания"
- "Внешние системы могут проверить, подписал ли пользователь определенный документ"
- "Администратор может добавлять новые шаблоны документов в систему"
- "Пользователь получает уведомление при появлении нового документа на подпись"

**Примеры плохих критериев приемки:**
- ❌ "Разработан REST API метод GET /api/documents" (техническая деталь)
- ❌ "Время ответа API не превышает 500 мс" (нефункциональное требование)
- ❌ "Кнопка 'Подписать' окрашена в зеленый цвет" (деталь UI)

### 8. Критерии готовности (DoD)

**Обязательный раздел.**

Критерии готовности (Definition of Done) — это конкретные технические задачи и проверки, которые необходимо выполнить для достижения критериев приемки. В отличие от критериев приемки, которые фокусируются на бизнес-ценности, критерии готовности описывают технические аспекты реализации.

**Основные принципы формулирования критериев готовности:**

1. **Фокус на технических деталях:**
   - Описывайте конкретные технические задачи, которые нужно выполнить
   - Указывайте специфические технические решения, необходимые для реализации
   - Пример: ✅ "Реализован REST-API метод GET /api/v1/documents с поддержкой параметров фильтрации"

2. **Конкретность и измеримость:**
   - Критерии должны быть конкретными и проверяемыми
   - Должна быть возможность однозначно определить, выполнен критерий или нет
   - Пример: ✅ "Настроено преобразование данных из формата A в формат B"

3. **Связь с критериями приемки:**
   - Каждый критерий готовности должен способствовать достижению одного или нескольких критериев приемки
   - Должно быть понятно, как выполнение технической задачи приближает к достижению бизнес-цели

**Что ДОЛЖНО быть в критериях готовности:**
- Конкретные технические задачи (например, "Реализован метод API", "Настроена интеграция с системой X")
- Специфические технические решения (например, "Добавлена поддержка параметра Y в запросе")
- Технические аспекты безопасности и производительности (например, "Настроена аутентификация для API")

**Что НЕ должно быть в критериях готовности:**
- ❌ Общие очевидные вещи (например, "Написаны unit-тесты", "Код прошел ревью")
- ❌ Повторение критериев приемки
- ❌ Организационные моменты (например, "Получено подтверждение от заказчика")

**Примеры хороших критериев готовности:**
- "Реализован REST-API метод GET /api/v1/documents с поддержкой параметров фильтрации по дате и статусу"
- "Настроено преобразование данных из формата JSON в протобуф для интеграции с микросервисом X"
- "Добавлена поддержка параметра org_id в запросе для фильтрации по организации"
- "Настроена аутентификация и авторизация для API методов"
- "Реализована обработка всех возможных комбинаций входных параметров"

**Примеры плохих критериев готовности:**
- ❌ "Написаны и успешно пройдены unit-тесты" (очевидная вещь)
- ❌ "Код прошел ревью и соответствует стандартам кодирования" (очевидная вещь)
- ❌ "Документация API обновлена в Swagger" (очевидная вещь)

### Создание шаблона
Открывает по плюсику предтавляет из себя окно с полями:
Название шаблона и Контент шаблона, а также минималистичного AI-ассистента: AI-ревью
#### Название шаблона
Сюда пользователь вводит имя нового шаблона

#### Контент шаблона
Сюда пользовватель заполняет контент шаблона. Поле должна быть как flutter_code_editor

#### AI-ревью
model для AI-ревью используется таже, что и в основном конфиге для AI-асистента. При необходимости пользователь может изменить модель для ревью (модель для ревью также сохраняется в конфиге)
model: <название модели> по аналогии с AI-асистентом кликабельна и открывает список для выбора, где доступно 10 опций, а если провайдер вернул больше, то раскрывающийся список
По кнопке "Отправить на ревью" выполняется запрос в ИИ со следующим промтом:

```promt
Ты AI-ассистент в программе NovaSpec, и в рамках данного запроса пользователь отпавляет тебе на ревью свой шаблон ${тип шаблона}.
Ты как методолог системных/бизнес аналитиков должен провести ревью шаблона и дать свою экспертную оценку и рекомендации по изменению шаблона.
В рамках своей экспертной оценки ты должен разделить свои комментарии на критические и рекомендации.
Критические указываешь, если в шаблоне есть явные несостыковки, которые могут привести генерацию артефакта по данному шаблону к негативным последствиям
А рекомендации, если это не сильно повлияет на конечный результат.
Если есть критические замечания, то в ответе обязательно указывай тег @critical_alert, тогда приложение посчитает, что AI-ревью не пройдено и пользователь не сможет сохранить шаблон. 
Относись к критическим замечаниям максимально серьезно! Не стоит по мелачам проставлять замечание как критическое, иначе пользователь перестанет воспринимать тебя в серьез
```

Также в промте надо учесть требования, чтобы ответ от ИИ был в режиме стриминга с JSON, чтобы ответ от ИИ корректно отображался в диалоге

Если по результату ревью нет критических замечаний, то кнопка Сохранить становится для доступна для нажатия, иначе она остается неактивной.
Пользователь при желании может Сохранить шаблон без ревью, кнопка доступна всегда
Если пользователь передумал создавать шаблон может нажимать кнопку Отмена
